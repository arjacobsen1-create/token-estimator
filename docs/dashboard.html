⇶Workflows — Multi-step AI Cost Forecasting

The estimator above prices one prompt and one reply; a workflow is a multi-step agent run where the history is billed again at every step, and this mode prices the run.

How this works

At every step the model receives the instruction, the retrieved material and everything the earlier steps produced, and that history is billed again. This mode prices the run, and shows what the way you carry the history costs.

Context sent at each step — full carry

How to read this: the baseline prices the same steps independently, each sent fresh with only the starting context: no accumulated history, no retries. Same model and task configuration; different execution assumptions. A retry re-sends that step's call with the same context, billed in full, until the step succeeds. Caching, when on, is idealised cache reuse: repeated prefixes priced at 10% of the input price; real hit rates vary by provider, and a summary that changes every step is not a stable prefix. Monthly figures are expected spend, not a guaranteed bill. Reasoning tokens, when set, are priced as output. Retaining the most history does not by itself make a mode the highest-quality architecture. This mode forecasts model consumption only: it does not price infrastructure, and it does not measure answer quality.

How this works

Each agent is priced by the same Workflows engine: at every step the model receives the starting context plus whatever history its context mode carries, and that history is billed again. Retries use the Workflows default of 10%; retries are billed. A failed call is billed in full and retried, so retries multiply the main calls; in Summarised mode the summary calls on the fast tier are included in both the cost and the token count. The reply at each step is predicted from the shared task type, the same prediction Workflows uses. Prices are the published reference prices used everywhere in this app, not live supplier quotations. This compares estimated consumption only: a lower estimated cost does not establish that an agent does the job better.

✂Minimiser — Reduce the Prompt, Cap the Reply

Use fewer tokens. Preserve the intent.

Paste a prompt: the minimiser shrinks it and predicts the reply, because a tiny prompt can trigger a huge, expensive answer.

How this works

The third module of this product, running on the same shared engine and the same price table as everything above. It minimises the total, input plus predicted output, and reports the saving as a range, framed by how you pay.

The minimised text is the same for every model. The model only changes the token counter and the prices.

    ⓘWhat this measures, and what it doesn't

    It measures
    • Input tokens: the material handed to the model, counted. Exact for GPT models (the real o200k_base tokenizer); labelled estimates for other models, with the measured error published in ACCURACY.md.
    • Predicted output tokens: forecast from the type of task (summarise about 0.2x the input, extract 0.3x, draft 1.5x, code 2x, classify a fixed short label). A forecast, not a meter reading.
    • Cost: input plus predicted output, at the selected model's price, at your volume. Prices are editable defaults.
    • For the SAP edition: 21 generic shapes of SAP work with typical input sizes, published in SAP-TASKS.md. No client data, no system data.
    It doesn't measure
    • Quality: a cheaper run is not a better run. Nothing here scores the answer.
    • Actual consumption: only a metered bill or platform telemetry proves what a workload really used.
    • Vendor consumption units (SAP AI Units and the like): vendors set conversion rates per scenario. This measures the token driver underneath, which is what every basis converts from.
    • Business value: whether a task was worth doing at all stays a human decision.

    If you pay a flat subscription, read the dollar figures as an API-equivalent yardstick: they size and compare workloads and show what burns the allowance you already bought. If you pay per token or in consumption units, they are a direct forecast. Either way the tool prices the work, not the channel: Joule, in-tenant agents, plugins and direct APIs all consume the same tokens. Governance differs by channel, so anonymise before anything leaves the tenant (protections list in SAP-TASKS.md).
